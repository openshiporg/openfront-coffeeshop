## Blocker

### QA-101: Most dashboard record pages say "Not found", five Models lists fail, and the cafe order page crashes
- **Area:** dashboard
- **URL:** for example `/dashboard/menu-items/cmvk5c1oh000sp701sci611c4`, `/dashboard/inventory-items/cmvk5c1ng000cp701lymrnymq`, `/dashboard/store-settings/cmvk5c1ml0002p701xs9lhp7a`, `/dashboard/cafe-orders/cmvlhlvrr001smk01bmqj0hrr`, `/dashboard/inventory-items` (list)
- **Steps:** Sign in. Open Models › Inventory Items, Stock Movements, Ingredients, Prep Batch Consumptions or Menu Item Images. Then open any record of Menu Items, Inventory Items, Store settings, Ingredients, Menu Item Images, Recipes, Purchase Orders, Menu Item Modifiers or Stock Movements. The Menu manager's "Full record ↗" links lead to the same pages.
- **Expected:** Each list loads, and each record opens in its edit form.
- **Actual:**
  - The five lists show "Failed to load items: Unable to complete the request. Please try again."
  - The record pages show "Not found. The item with ID … doesn't exist, or you don't have access to it."
  - `/dashboard/cafe-orders/[id]` shows the "Something went wrong" error boundary.
  - The console logs "Dashboard operation failed (details redacted)." (65 times in one crawl).
  - Only lists and records with none of the shifted field types work (Suppliers, POS orders, Menu Item Modifiers list).
  - The same GraphQL fields query fine directly, so the data is intact.
  - The merchant can't edit a menu item's description or recipe, an inventory item's supplier or reorder point, or the Store settings record. They can't open an order record either.
- **Root cause (confirmed):**
  - Round 1 changed `StoreSetting.taxRateBasisPoints` from integer to **decimal**. `StoreSetting` is registered early, so Keystone now assigns the `decimal` view index 9. The live admin meta shows 9=decimal, 10=document, 11=virtual, 12=multiselect, 13=image.
  - The committed `features/keystone/view-order/index.ts` still has the old order, with `decimal` last (…9=document, 10=virtual, 11=multiselect, 12=image, 13=decimal). It was not regenerated with the schema.
  - So `getFieldTypeFromViewsIndex` maps every decimal field to `document` (`currentStock { document(…) }`), images to `decimal` (a bare `image`), multiselects to `image`, and so on. Each query is then invalid.
- **Fix:** Regenerate the view order: `tsx features/keystone/view-order/generate-view-order.ts`, which is part of `npm run migrate:gen`. Commit the new `features/keystone/view-order/index.ts` and redeploy. Consider a parity or CI check that the committed VIEW_ORDER matches the built schema.
- **Likely files:** `features/keystone/view-order/index.ts`, `features/dashboard/views/getFieldTypeFromViewsIndex.ts`, `features/dashboard/actions/getListItemsAction.ts`, `features/dashboard/actions/getItemAction.ts`.

## Major

### QA-102: Staff can't accept an order-ahead request while closed, and the dashboard hides the reason
- **Area:** dashboard
- **URL:** `/dashboard/platform/orders`
- **Steps:**
  1. After closing, place a pickup order on the storefront for tomorrow 8:15 AM (#CF-261023-16E4CEDA).
  2. In Orders, tap "Accept unpaid pickup" on it.
- **Expected:** The request can be confirmed tonight for tomorrow's slot, and stock is held for it. If acceptance isn't allowed yet, the button says so, for example "Opens 8 AM, accept after opening".
- **Actual:**
  - The red text "Unable to complete the request. Please try again." appears under the button.
  - Calling the mutation directly returns the real reason: `"The cafe is closed for pickup at that time"` (code `CAFE_CUSTOMER_ERROR`). `admitOpenCafeOrder` runs `assertCoffeeOrderingAvailable(settings, now)`, and the line check does the same with `at = now`.
  - "Record cash" and "Record card" for the same request go through the same admission path.
  - Consequences:
    - The customer's receipt says "waiting for acceptance" all night.
    - Stock isn't consumed until acceptance, so overnight requests aren't held against stock and can oversell the first morning slots.
    - At opening, staff must accept every overnight request at once.
- **Likely files:**
  - `features/keystone/mutations/acceptCafePickupOrder.ts:128-150` (`admitOpenCafeOrder`, `assertCafePickupAcceptanceAvailability`): check only `promisedAt` for an order-ahead request.
  - `features/dashboard/lib/security.ts` (`PUBLIC_REQUEST_ERROR`): let `CAFE_CUSTOMER_ERROR` messages through to staff.
  - `features/platform/orders/actions/order-status.ts`, `features/platform/orders/components/OrderStatusActions.tsx:86`.
